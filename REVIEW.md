# Проверка решения

Версия подготовлена 13 ноября 2026 года для предварительного просмотра.

## Что изменено

- HTTP, бизнес-операции, SQL и внешние адаптеры разделены по модулям.
- Шлюз и webhook вызываются после завершения транзакции БД. Тест получает `FOR UPDATE NOWAIT` из независимой сессии во время обоих вызовов.
- Прикладные ошибки шлюза и адаптера доставки ограничены тремя попытками с интервалами 1 и 2 секунды; повтор планируется транзакционным outbox.
- При повторе после успешной обработки шлюз не вызывается заново. Неуспешная доставка не меняет финансовый результат.
- Некорректные сообщения и ошибки, при которых нельзя записать состояние в БД, ограничены политикой redelivery RabbitMQ и переходят в DLQ.
- `/health` также требует API key; healthcheck Compose передаёт его.

## Выполненные проверки

- `python -m pytest -q`: 11 тестов с отдельной настоящей PostgreSQL.
- `ruff check app migrations tests examples`: без ошибок.
- `alembic upgrade head` и `alembic check`: миграция применена, расхождений нет.
- `examples/smoke.py`: настоящие API, PostgreSQL, RabbitMQ, consumer и HTTP-получатель; доставка с первого раза, после двух HTTP-ошибок, отказ после трёх попыток; повтор POST и стабильный event_id.
- `examples/poison_smoke.py`: некорректный UUID в сообщении попал в настоящую DLQ с `x-death.reason=delivery_limit`.

Чистая сборка из Docker Hub в этой сессии зависла на получении базового образа и была остановлена. Сквозные проверки выполнены в изолированном Compose-проекте на ранее установленном образе этого же проекта с текущим исходным кодом, подключённым read-only; зависимости не менялись. Успешную чистую сборку с нуля эта проверка не подтверждает.

## Принятые границы

At-least-once означает возможный повтор внешнего действия при аварии до записи результата. Эмулятор шлюза и получатель webhook используют стабильные ключи идемпотентности; exactly-once не заявляется. Невалидное или неизвестное сообщение может попасть в DLQ без изменения платежа. После окончательной технической ошибки шлюза ставится `failed/dead`, разбор выполняется из DLQ. При DB outage backoff прикладных попыток не гарантируется: действует отдельный конечный broker redelivery.

Outbox relay держит только блокировки outbox во время publisher confirm с ограниченным тайм-аутом; платежи на это время не блокируются. Это сознательное упрощение тестового решения, описанное в README.
